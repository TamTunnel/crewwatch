Crewwatch

A persistent manager agent that owns an engineering goal end-to-end on free local coding agents — and proves what it did. It breaks a goal into tasks, dispatches each to a coding agent on your own machine, and closes a task only when the repo's own tests pass. Every finished task gets a signed receipt. It never merges anything itself.

Repository on GitHub · Apache-2.0 · Go stdlib-first single binary · SQLite state

What makes it different

  • Verification-first closing. A task closes only when the repo's own tests pass in the worker's worktree. A worker's claim of “done” is never sufficient — test-gutting escalates, it doesn't ship.
  • The eval harness is the product. A benchmark of real engineering tasks across two repos, run on every release, with completion rate, attempts, and cost recorded — not claimed. The full results JSON for this run is below.
  • Signed receipts, not chat transcripts. Every closed task emits an Ed25519-signed, content-addressed crewwatch/1 receipt — what was done, which worker, how many attempts, what it cost — verifiable offline with crewwatch verify.
  • Worktree isolation. Every worker runs in its own git worktree. Writes outside it to the main checkout, other worktrees, .git/hooks, or the state home are detected and escalate the task.
  • Crash-safe by design. SQLite state, kill -9 the daemon mid-goal and it resumes with no lost tasks and no duplicated dispatches. Bounded repair: unfixable tasks escalate at their attempt budget.
  • Human gate. Verified work waits in its worktree branch. Crewwatch never merges and never pushes — there is no code path from a verified task to a merge.

Honest limits — stated, not hidden

  • Harness workers are scripted fixers, so the 10/10 measures the manager pipeline (dispatch, verify, receipt), not model capability. Real CLI adapters (OpenCode, Qwen Code, Claude Code, Codex, Gemini CLI) are exercised with stub CLIs in the adapter tests; no live model run has happened in this environment. Long-horizon reliability on real models is unproven — the harness exists to measure it, not hide it.
  • Workers run with your credentials and filesystem access (no sandbox in v1). A worker can read your home directory and environment. This is disclosed in the README, in --help, and on stderr on every dispatch. A real sandbox is a v1.1 assessment.
  • Escape detection covers an inventory, not the filesystem. The main checkout (including gitignored files and .git/hooks), every other live worktree, and the state home's top level are snapshotted before dispatch and compared after. A worker that writes somewhere entirely outside those snapshots (e.g. an arbitrary path in /tmp) is not detected — and that enables nothing beyond the already-accepted no-sandbox residual.
  • Green tests ≠ correct. Verification via the repo's own tests only works if the repo has tests, and tests can pass on wrong code. The verifier is necessary, not sufficient.
  • Receipts and the audit log are tamper-evident only against anyone who lacks the operator's keys. A worker on this machine has operator credentials in v1 and could read key.pem/audit.key and forge receipts or rewrite the log that would still verify. That exposure is a revocation event: replace the keys, and receipts from before the rotation fail verification by design.
  • Verification executes worker-controlled code as the manager. go test runs the worker's TestMain/init functions — “verify” is itself code execution of untrusted output. An accepted no-sandbox consequence in v1, not a separate sandbox boundary.
  • Free local models are weaker than frontier models. The cost pitch is real; the capability ceiling is lower than Devin's. The harness must show the gap honestly.

Run it yourself

git clone https://github.com/TamTunnel/crewwatch.git
cd crewwatch
go build -o build/crewwatch ./cmd/crewwatch

# Add a goal (JSON spec; see examples/goal.json)
./build/crewwatch goal add --spec examples/goal.json

# Run the daemon (leave it running; it picks up goals and works them)
./build/crewwatch daemon

# Check progress, verify receipts, run the benchmark
./build/crewwatch status
./build/crewwatch verify --all
./build/crewwatch eval --out eval/results
